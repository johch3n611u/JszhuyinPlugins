## 0. 一句話結論

青简的「英文查字典」不是單一功能，而是**兩條互不相干的資料線**：

| 線 | 資料檔案 | 作用 |
|---|---|---|
| **A. 英文詞表** | `assets/lexicon/english.tsv`（94,568 詞） | 打英文字母時出英文**候選**（精確詞 / 前綴補全 / 拼錯糾正 / 混輸） |
| **B. 釋義表** | `glossary-en.tsv`（232,213）<br>`glossary-zh.tsv`（44,924） | 候選**右側那一行譯詞**（`开发 → development`） |

README 裡那個「候選旁的譯詞」是線 B；真正「用英文字母查字典出候選」是線 A。兩者的查詢路徑、資料結構、載入時機都分開，只在 `Engine::annotate()` 之後才串起來。

青简英文能力最值得看的不是「有一張詞表」，而是**用語言模型比分決定「這段輸入該按中文讀還是英文讀」**，以及比分時**刻意排除個人加成**的那個設計（見 [2.5](#25-查詢路徑-拼音頭--英文尾)）。

## 1. 兩條獨立的英文資料線

```
                         ┌─────────────────────────────────────────────┐
                         │  線 A：english.tsv（英文詞表）               │
                         │  誰產生候選？怎麼排序？怎麼糾錯？            │
                         └───────────────────┬─────────────────────────┘
                                             │  Engine::query()
                                             ↓
   使用者按鍵 ──→ Composition ──→ query_inner() ──→ CandidateList
                                             │  Engine::annotate()
                                             ↓
                         ┌─────────────────────────────────────────────┐
                         │  線 B：glossary-*.tsv / .qj（釋義表）        │
                         │  候選已經排好了，只是給每個候選掛一行譯詞    │
                         └─────────────────────────────────────────────┘
```

關鍵分離點：

- **A 在 `query()` 階段**，決定候選本身
- **B 在 `annotate()` 階段**（`crates/qingjian-core/src/engine/commit/mod.rs:28`），只給已排序的候選掛譯詞
- 釋義表**查不到就留空**，不影響候選產生與排序

這個分離是有意的：釋義表可以隨時換語言（英 / 日 / 西）、可以關掉（`learning_language = off`）、可以雲端兜底補寫，都不需要動候選管線。

## 2. 線 A：英文詞表（候選產生）

### 2.1 資料流水線

詞表不是手寫的，是三道離線加工產出（執行期零網路）。

**上游來源**（`assets/lexicon/05_english/`，114,876 詞形）：

| 檔案 | 內容 | 來源 |
|---|---|---|
| `00_all_words.tsv` | 英文補全總表 | ESDB / CSpell（MIT） |
| `01_common.tsv` | 常用詞（帶詞性、詞元） | 同上 |
| `02_extended.tsv` | 擴展詞 | 同上 |
| `03_proper_nouns_abbreviations.tsv` | 專名與縮寫 | 同上 |
| `04_inflections.tsv` | 詞形變化（lemma → form） | 同上 |
| `06_misspellings.tsv` | 誤拼對照 | typos |
| `07_display_forms.tsv` | 大小寫修正（`Windows` / `GitHub` / `VSCode`） | 人工整理 |

**加工指令**（見 `assets/lexicon/QINGJIAN.md` 第 5 步）：

```bash
# 1. 詞形合併 + 大小寫修正
cargo run --release -p qingjian-dict-convert -- english \
    assets/lexicon/05_english/00_all_words.tsv \
    assets/lexicon/05_english/07_display_forms.tsv

# 2. 用 wordfreq 算詞頻（Zipf × 1000）
uv run tools/corpus/english_frequency.py \
    data/generated/english.tsv -o data/generated/english-frequency.tsv

# 3. 再跑一次，把詞頻寫進第三欄
cargo run --release -p qingjian-dict-convert -- english \
    assets/lexicon/05_english/00_all_words.tsv \
    assets/lexicon/05_english/07_display_forms.tsv \
    --frequency data/generated/english-frequency.tsv
```

**最終格式**（`assets/lexicon/english.tsv`）：

```tsv
# 由 qingjian-dict-convert english 生成。词\t编码\t词频（wordfreq 的 Zipf 频率 ×1000）
a	a	7360
aardvark	aardvark	2390
abandon	abandon	4019
iPhone	iphone	800
```

第三欄是 **wordfreq 的 Zipf 頻率 × 1000**。Zipf 7.36 ≈ 每十億詞出現 10^7.36 次，也就是 `a` 是極高頻詞。

**加工器的兩條規則**（`tools/dict-convert/src/english.rs`）：

```rust
// 同一文件内先到先得（数据包按常用度排序，第一个就是最常用的写法）
if !seen_in_file.insert(code.clone()) { continue; }
match index_by_code.get(&code) {
    // 后面的文件覆盖前面的：展示写法补充表用这条把 `windows` 顶成 `Windows`
    Some(&index) => rows[index].0 = word.to_owned(),
    None => { index_by_code.insert(code.clone(), rows.len()); rows.push(...); }
}
```

設計要點：

1. **同一檔案內先到先得** — 因為上游資料包已按常用度排序，保留第一個就是保留最常用寫法
2. **後面的檔案覆蓋前面的** — `07_display_forms.tsv` 就是靠這條把小寫 `windows` 頂成 `Windows`
3. **覆蓋時位置不動** — 只換字面，順位保留，不會因為多了 `Windows` 就把 `Windows` 挪到詞表末尾
4. 只收純字母詞；表頭行 `word\tkey` 自然被過濾掉

### 2.2 資料結構 `WordList`

**檔案**：`crates/qingjian-dictionary/src/word_list.rs`

```rust
pub struct WordList {
    /// 小写编码 → 在 `entries` 里的下标
    by_code: HashMap<String, usize>,
    /// (编码, 原样词, 词频)，按编码字节序排好，前缀补全二分定位
    entries: Vec<(String, String, u32)>,
}
```

**不是 trie，是 HashMap + 排序陣列**。四個操作對應四種結構：

| 方法 | 實作 | 複雜度 |
|---|---|---|
| `get(code)` | `by_code.get()` | O(1) 精確查 |
| `frequency(code)` | 同上，多回傳第三欄 | O(1) |
| `complete(prefix, limit)` | `partition_point` 二分定位起點 → `take_while` 掃前綴區間 → 按詞頻降序取前 N | O(log n + 區間長度) |
| `entries()` | 全量 iterator | O(n) |

`complete()` 的實作：

```rust
let start = self.entries.partition_point(|(code, _, _)| code.as_str() < prefix);
let mut hits: Vec<&(String, String, u32)> = self.entries[start..]
    .iter()
    .take_while(|(code, _, _)| code.starts_with(prefix))
    .filter(|(code, _, _)| code != prefix)   // 不含正好相等的
    .collect();
hits.sort_by(|a, b| b.2.cmp(&a.2).then_with(|| a.0.cmp(&b.0)));  // 詞頻降序，同頻按編碼
hits.into_iter().take(limit).map(|(_, word, _)| word.as_str()).collect()
```

**為什麼不用 trie**：拼錯糾正要算編輯距離，任何索引都用不上，只能全掃 `entries()`。94k 詞規模下 HashMap + 排序陣列夠用，且記憶體緊湊、實作簡單。

**大小寫處理**：鍵始終小寫，值保留原樣寫法（`iPhone`）。查詢時呼叫方負責先 `to_ascii_lowercase()`。

### 2.3 查詢路徑 ①：英文模式

**觸發**：殼裡 Caps Lock 亮著（`engine.english_mode = true`）

**檔案**：`crates/qingjian-core/src/engine/query/modes.rs:72` → `crates/qingjian-core/src/english/mod.rs:17`

```rust
pub fn suggest(
    lists: &[&WordList],        // 个人表在前、随包表在后
    typed: &str,
    weight: impl Fn(&str) -> u32,  // 用户选过多少次
    limit: usize,                  // ENGLISH_MODE_CANDIDATES = 18
) -> Vec<String>
```

**三段式，嚴格依序**：

```
1. 精確命中   — lists 裡第一個有的詞，直接放第一
2. 前綴補全   — 兩張表的命中【合併】後統一排序
3. 拼錯糾正   — 只在 len ≥ 4 且純字母時才做
```

**排序鍵**（`ranked` 閉包）：

```rust
weight(b.0).cmp(&weight(a.0))          // 1. 使用者選過的次數（個人學習）
    .then_with(|| b.1.cmp(&a.1))       // 2. 詞表詞頻
    .then_with(|| a.0.cmp(&b.0))       // 3. 編碼字典序（保證確定性）
```

**大小寫跟隨輸入**（`adapt_case()`）：

| 輸入 | 詞表寫法 | 輸出 | 規則 |
|---|---|---|---|
| `comp` | company | `company` | 全小寫 → 照詞表 |
| `Comp` | company | `Company` | 首字母大寫 → 首字母大寫 |
| `COMP` | company | `COMPANY` | 全大寫 → 全大寫 |
| `Iphone` | iPhone | `IPhone` | 首字母大寫 → 首字母大寫（不照詞表的 iPhone） |
| `iphone` | iPhone | `iPhone` | 小寫輸入照詞表 |

判定：

```rust
let first_upper = chars.next().is_some_and(|c| c.is_ascii_uppercase());
let rest_upper = typed.len() >= 2 && typed.chars().all(|c| !c.is_ascii_lowercase());
```

**emoji 排最後**：`query_english()` 在 `suggest()` 之後插 emoji，然後 `sort_by_key(|c| c.kind == Emoji)` 把 emoji 全推到末尾。原因寫在原始碼註釋：選詞靠上下鍵，emoji 夾在詞中間會擋路。

### 2.4 查詢路徑 ②：中英混輸整詞

**觸發**：中文模式下打的整段字母**恰好是一個英文詞**（`agent`、`database`、`cargo`）

**檔案**：`crates/qingjian-core/src/engine/extras.rs:64` `insert_english()`

```rust
let word = lists.iter().find_map(|words| words.get(text));  // 整段查詞表
```

**候選位置的判定**（原始碼邏輯）：

```rust
// 这段字母下用户选中文词（`key` → 可以）比选英文词的次数多：中文词留在第一
let chosen = items.first()
    .filter(|c| c.kind == Chinese)
    .map_or(0, |c| self.learner.choice_weight(text, &c.text));
let english_weight = word.map_or(0, |w| self.learner.weight(w));

// 两字母全大写缩写（mp → MP、bm → BM）让中文先：整段太短，几乎总是在打中文
let short_acronym = english_weight == 0
    && text.len() <= 2
    && word.is_some_and(|w| w.chars().all(|c| c.is_ascii_uppercase()));

let english_first = !self.chinese_first && unlikely_pinyin
                    && chosen <= english_weight && !short_acronym;
```

**四條規則疊加**：

1. **拼音不像話**（`unlikely_pinyin`）時英文才排第一 — 切不動、或除末尾外還有聲母縮寫 / 殘缺音節
2. **不壓過使用者學習記錄** — `chosen <= english_weight`：這段字母下使用者選中文詞更多，中文就留在第一（「拼音再不像話也是他自己教的」）
3. **兩字母全大寫縮寫例外** — `mp` / `bm` 整段太短，幾乎總在打中文（門票、編碼），讓中文先
4. **例外只管沒選過的詞** — 使用者選過 OK，下次敲 `ok` 照樣 OK 排第一

**英文補全**（僅 `unlikely_pinyin` 且長度 ≥ 3 時）：

```rust
if unlikely_pinyin && text.len() >= MIN_COMPLETION_LETTERS {  // 3
    let mut budget = ENGLISH_COMPLETIONS;  // 3
    for words in &lists {                  // 个人表优先
        for word in words.complete(text, budget) {
            // 去重后插入，紧接在精确词之后
            budget -= 1;
        }
        if budget == 0 { break; }
    }
}
```

`compa` → company / compare / compass，最多 3 條。

### 2.5 查詢路徑 ③：拼音頭 + 英文尾

**這是青简英文能力裡最有意思的部分。**

**觸發**：整段輸入尾部是一個英文詞，前面是合法拼音

```
woxiangxuehaorust  →  头 woxiangxuehao  +  尾 rust
wodedatabase       →  我的 + database（不切成 我的大塔巴瑟）
womenqubeijing     →  我们去北京（整段拼音赢，不切）
taida              →  太大 赢过 他 + Ida
huoz               →  或者 赢过 和 + Oz
```

**檔案**：`crates/qingjian-core/src/engine/query/english_tail.rs:37`

#### 切分嘗試

```rust
let longest = scope.len() - MIN_ENGLISH_TAIL_HEAD_LETTERS;  // 头至少 2 字母
(MIN_ENGLISH_TAIL_LETTERS..=longest).rev()                   // 尾从长到短试
    .find_map(|len| { ... })
```

**從長到短試尾段**，同時滿足全部條件才切：

| 條件 | 常數 | 說明 |
|---|---|---|
| 尾段必須在英文詞表裡 | — | 隨包表或個人表 |
| 頭段必須能切成完整拼音節 | — | `parser::is_fully_segmentable(&scope[..head_len])` |
| 尾段若是完整拼音，要夠長 | `MIN_PINYIN_LIKE_TAIL_LETTERS = 4` | `database` → `da ta ba se` 能切，但要 ≥ 4 字母 |
| 2 字母尾段只認縮寫或個人詞 | — | `to` / `it` 太容易撞簡拼；`ID` / `TV` / `OK` 可以 |
| 雙拼輸入不切 | — | `shuangpin.is_some()` 直接回傳 None |
| 帶 `'` 的輸入不切 | — | — |
| 整段已是英文詞不切 | — | `agent` 走路徑 ②，那條本來就排第一 |
| 拼寫糾錯能糾通就不切 | — | `shiide` → 是的，那是敲錯不是英文 |
| 有英文補全就不切 | — | `releas` → release，那條路本來就排第一 |

其中一條特別值得注意（原始碼註釋）：

```
// 个人表不算：打不出来时原样上屏会把整串失败的拼音（`woxiangxuexirust`）学成「英文词」，
// 再拿它把混输这条路堵掉就是死循环——越打不出来学得越多，越学越打不出来
if self.english.as_ref().is_some_and(|words| words.get(scope).is_some()) { return None; }
```

個人詞表被刻意排除在「整段是英文詞」的判定之外，否則會形成正回饋死循環。

#### 比分決策（核心）

`split_english_tail()` 只說明「可以這麼讀」，**不代表就這麼讀**。誰排前面由 `mixed_beats_plain()` 比分決定。

**檔案**：`english_tail.rs:118`

```rust
let comparable = |c: &Conversion| c.static_score - c.penalty;

let mixed  = comparable(&head) + tail.log_prob - ENGLISH_SWITCH_PENALTY;
let plain_score = comparable(&plain);

mixed > plain_score   // → 按英文读
```

其中：

```
log_P = (zipf − 9) · ln(10)
```

詞頻來自 wordfreq 的 Zipf × 1000，除以 1000 還原成 Zipf 值。沒有詞頻的（`kubectl` 這類技術詞）墊底到 `ENGLISH_ZIPF_FLOOR = 3.0`。

`ENGLISH_SWITCH_PENALTY = 3.0` 是切到英文的固定代價。

#### 最關鍵的設計：比分時排除個人加成

原始碼註釋寫得非常直白：

```
/// 两边比的是 `static_score - penalty`（静态语言模型 + 敲错代价），**不含个人 n-gram 与用户加分**：
/// 头段只覆盖一部分音节，整段读法多出来的那几个音节会白拿一份按长度累积的个人加成。
/// `woxiangxuexirust` 上实测头段拿 +6.9、整段拿 +21.2，个人模型越肥差距越大——
/// 用户打得越多混输越打不出来。这是「哪种输入方式」的判断，本来也该由静态模型定，不归个人频次管。
```

**問題**：個人 n-gram 是按音節數量累加的。整段按拼音讀會覆蓋更多音節，因此白拿更多個人加成——個人模型越用越肥，混輸就越來越難觸發。

**解法**：這個判斷本質上是「使用者想用哪種輸入方式」，屬於策略問題，不該由個人頻次決定。所以**靜態分比**，個人加成只在最終候選排序時才計入。

這是個很深的洞察，也是整個英文能力設計裡最值得借鑑的一點。

### 2.6 拼錯修正 `within_one_edit`

**檔案**：`crates/qingjian-core/src/english/edit.rs:6`

不是 Levenshtein DP，是四種情形的手寫判斷：

```rust
pub fn within_one_edit(a: &str, b: &str) -> bool {
    match a.len().abs_diff(b.len()) {
        0 => same_length(a, b),        // 最多一个位置不同，或恰好相邻两位对调
        1 => one_insertion(short, long), // 去掉一个字节后相等
        _ => false,                     // 差两处以上，直接否
    }
}
```

**等長分支**（`same_length`）：

```rust
let mut differences = a.iter().zip(b).enumerate().filter(|(_, (x, y))| x != y);
let Some((first, _)) = differences.next() else { return true; };  // 完全相等
match differences.next() {
    None => true,                                   // 只有一个位置不同
    Some((second, _)) => {
        second == first + 1                         // 必须是相邻位置
            && a[first] == b[second]                // 且两字节互换
            && a[second] == b[first]
            && differences.next().is_none()         // 且没有第三个差异
    }
}
```

**單邊分支**（`one_insertion`）：

```rust
let mut i = 0;
let mut skipped = false;
for &byte in long {
    if i < short.len() && short[i] == byte { i += 1; }
    else if skipped { return false; }
    else { skipped = true; }
}
true
```

**觸發門檻**（`english/mod.rs`）：

```rust
/// 拼错纠正至少要几个字母：三个字母以内一处编辑能变出太多词，只补全不纠正。
pub const MIN_CORRECTION_LETTERS: usize = 4;

let letters_only = code.bytes().all(|b| b.is_ascii_lowercase());
if letters_only && code.len() >= MIN_CORRECTION_LETTERS && result.len() < limit { ... }
```

兩個限制：

- **≥ 4 字母**才糾正 — `hlo` 太短，一處編輯能變出的詞太多
- **純字母**才糾正 — `foo1`、`x_y` 是識別字串不是拼錯的詞，不去猜

測試用例覆蓋：

```rust
assert!(within_one_edit("hello", "hello"));  // 相等
assert!(within_one_edit("hallo", "hello"));  // 替换
assert!(within_one_edit("helo", "hello"));   // 少一个
assert!(within_one_edit("helllo", "hello")); // 多一个
assert!(within_one_edit("hlelo", "hello"));  // 换位
assert!(!within_one_edit("hxllx", "hello")); // 差两处
assert!(!within_one_edit("hlleo", "hello")); // 换位两处
assert!(!within_one_edit("he", "hello"));    // 差三处
```

## 3. 線 B：釋義表（候選右側譯詞）

### 3.1 TSV 格式與解析

**格式**（`crates/qingjian-translate/src/lib.rs`）：

```
词\t[词性. ]译文[\t[词性. ]译文][|读音]
```

- 最多取 `Translation::MAX_SENSES` 條義項
- `#` 開頭為註解行
- UTF-8 **無 BOM**、LF 換行、按碼點排序
- **任一行缺詞或缺釋義，整張表載入失敗**（嚴格解析）

樣例：

```tsv
开发	v. develop	n. development
中文	Chinese language
私	私|わたし          ← 日文，| 後面是假名讀音
```

**解析規則**（`glossary/mod.rs` 的 `parse_sense`）：

```rust
// `v. develop` → 词性 + 译文；识别不出词性缩写时整段都是译文
// 译文后面 `|` 接的是读音（`n. 開発|かいはつ`）
if let Some((head, rest)) = field.split_once(' ')
    && head.ends_with('.')
    && let Ok(part_of_speech) = head.parse::<PartOfSpeech>() {
    return Sense { part_of_speech: Some(...), text: rest.trim().to_owned(), ... };
}
Sense { part_of_speech: None, text: field.to_owned(), ... }
```

**資料檔案**：

| 檔案 | 條目數 | 作用 |
|---|---|---|
| `glossary-en.tsv` | 232,213 | 中 → 英（主學習語言） |
| `glossary-zh.tsv` | 44,924 | 英 → 中（給英文候選掛中文釋義） |
| `glossary-ja.tsv` | — | 中 → 日 |
| `glossary-es.tsv` | — | 中 → 西 |

由 `qingjian-gloss-gen` 用 **LLM 生成**（`tools/gloss-gen/src/english.rs`）。

**詞彙等級表**（`assets/levels/levels-en.tsv`）：

```tsv
# levels	A1	A2	B1	B2	C1	C2
a	A1
```

CEFR 等級，來源 CEFR-J Wordlist + Octanove Vocabulary Profile，給詞彙統計按級數詞用，不參與候選排序。

### 3.2 `.qj` mmap 容器

啟動解析 20 多萬行 TSV 太慢，所以打包成 `.qj` 二進制容器直接 mmap。

**檔案**：`crates/qingjian-translate/src/glossary/mod.rs`

**四個 section**：

```rust
const TEXT_TAG:  [u8; 4] = *b"TEXT";   // 字符串 arena（所有词、译文、读音、词性缩写拼在一起）
const ENTRIES_TAG:[u8; 4] = *b"ENTR";  // 词条表：word_start / sense_start / word_len / sense_count
const SENSES_TAG: [u8; 4] = *b"SENS";  // 释义表：text/reading/pos 各一组 (offset, len)
const HASH_TAG:  [u8; 4] = *b"HASH";   // 哈希索引
```

**佈局**：

```
┌──────────────────────────────────────────────┐
│ TEXT arena                                   │
│ "开发" "v." "develop" "n." "development" ... │  ← 字符串连续存，其余表只存偏移
├──────────────────────────────────────────────┤
│ ENTR[]  { word_start: u32, sense_start: u32, │
│           word_len: u16, sense_count: u16 }  │
├──────────────────────────────────────────────┤
│ SENS[]  { text_start, reading_start,         │
│           pos_start, text_len, reading_len,  │
│           pos_len, reserved }                │
├──────────────────────────────────────────────┤
│ HASH[]  u32[]  開地址雜湊索引                │
└──────────────────────────────────────────────┘
```

**載入時逐條校驗**（防資料損壞）：

```rust
for entry in entries.iter() {
    // 偏移落在 arena 内，且在字符边界上
    if !in_arena(entry.word_start, entry.word_len)
        || entry.sense_start as usize + entry.sense_count as usize > senses.len() {
        return Err(GlossaryError::Corrupt("entry points outside the arena or sense table"));
    }
}
if !hash::is_valid(&index, entries.len()) {
    return Err(GlossaryError::Corrupt("hash index does not match the entry table"));
}
```

**查詢**（`impl Translator for Glossary`）：

```rust
fn translate(&self, text: &str) -> Option<Translation> {
    match &self.storage {
        Storage::Owned(map) => map.get(text).cloned(),   // TSV 模式
        Storage::Mapped { index, .. } => {
            let id = hash::find(index, text, |id| self.mapped_word(id).unwrap_or(""))?;
            self.mapped_translation(id)                  // mmap 模式，零拷贝读
        }
    }
}
```

雙模式：`.qj` 走 mmap + 雜湊索引；其他擴展名當 TSV 解析（樣例詞庫用）。

**自研容器庫**：`crates/qingjian-format` —— mmap 讀、零拷貝視圖、寫入器、雜湊索引。基礎詞庫 `dict.qj`、語言模型 `lm.qj`、領域詞庫 `dicts/*.qj` 都用同一套容器。

### 3.3 三層結構與雲端兜底

**檔案**：`crates/qingjian-translate/src/layered_translator.rs`

```
┌─────────────────────────────────────────┐
│ LayeredTranslator                       │
│   ├─ personal: PersonalGlossary         │  ← 优先查
│   │    user-glossary-en.tsv             │     云端兜底写入、用户可手改
│   └─ bundled: Glossary                  │  ← 查不到再查
│        glossary-en.qj（mmap，只读）     │
└─────────────────────────────────────────┘
```

```rust
fn translate(&self, text: &str) -> Option<Translation> {
    self.personal.translate(text).or_else(|| self.bundled.translate(text))
}

fn learn(&mut self, word: &str, translation: Translation) {
    self.personal.insert(word, translation);  // 云端兜底的结果写进个人表
}
```

**雲端兜底**（`crates/qingjian-core/src/engine/gloss/`）：

- 上屏後發現隨包表查不到 → 丟給 `GlossFiller` 在背景問雲端
- 結果經 `Translator::learn()` 寫進個人表，下次候選裡就有譯詞
- 殼定時調 `Engine::poll_glosses()` 取結果

**與聯想刻意分開走**（原始碼註釋）：

```
/// 与联想（`Predictor`）分开走：联想是「最新请求优先」、防抖会丢旧请求，兜底恰恰要「每个词都问到、慢点没关系」。
/// 接口同样非阻塞：`request` 只入队，结果由壳定时 `Engine::poll_glosses` 取。
```

介面同樣非阻塞：`request()` 只入隊，不做網路呼叫。預設 `NoGlossFiller` 什麼都不問。

**約束**（`engine/translator.rs`）：

```rust
/// 候选翻译 annotation 的提供方。实现必须是纯查表级别的开销，不能做网络请求。
pub trait Translator: Send {
    fn translate(&self, text: &str) -> Option<Translation>;
    fn learn(&mut self, _word: &str, _translation: Translation) {}
    fn flush(&mut self) {}
}
```

trait 文件明確寫著：`Translator::translate` **不能做網路請求**，必須是查表級開銷。網路兜底走的是另一個 trait（`GlossFiller`），結果非同步寫回。

### 3.4 英文候選的譯詞

**檔案**：`crates/qingjian-core/src/engine/commit/mod.rs:28`

```rust
pub fn annotate(&self, list: &mut CandidateList) -> AnnotationReport {
    for candidate in &mut list.items {
        let mut text = candidate.text.as_str();
        // 繁体模式：先用 traditional_map 还原成简体再查
        if self.traditional && let Some(simp) = traditional_map.get(text) {
            text = simp.as_str();
        }
        candidate.translation = match candidate.kind {
            CandidateKind::Custom(_) => None,   // 自定义短语不出译词
            // 英文候选按敲的大小写显示（Company / COMPANY），释义表键是小写
            CandidateKind::English => self.english_translator.translate(text)
                .or_else(|| self.english_translator.translate(&text.to_ascii_lowercase())),
            _ => self.translator.translate(text).map(|mut translation| {
                self.mark_fresh(&mut translation);
                translation
            }),
        };
    }
}
```

**兩個 Translator 分開**：

| 欄位 | 表 | 方向 | 用途 |
|---|---|---|---|
| `translator` | `glossary-en.qj` | 中 → 英 | 中文候選右側的英文譯詞 |
| `english_translator` | `glossary-zh.qj` | 英 → 中 | 英文候選右側的中文釋義 |

**大小寫 fallback**：英文候選顯示 `Company` / `COMPANY`（跟敲的走），但 `glossary-zh.tsv` 的鍵是小寫，所以先查原文、查不到再查小寫。

**繁體模式的處理**：`traditional_map` 記錄了「繁體 → 簡體」的映射（在 `query()` 階段產生），`annotate()` 時先還原成簡體再查釋義表——因為釋義表的鍵是簡體。

**統計**：`AnnotationReport { total, hits, elapsed }` 記錄嘗試標註數、命中數、耗時，供效能分析用。

## 5. 可借鑑的移植點

如果要把青简的英文能力移植到浮動注音小工具，按難度排序：

### 5.1 簡單：WordList + suggest（可直接搬）

青简的 `WordList` 是 **TSV + HashMap + 排序陣列**，無任何 Rust 依賴，94k 詞在 JS 裡跑 `complete()` 也夠快。

需要移植的檔案：

| 青简原始檔 | 說明 |
|---|---|
| `crates/qingjian-dictionary/src/word_list.rs` | 資料結構，~140 行 |
| `crates/qingjian-core/src/english/mod.rs` | `suggest()` + `adapt_case()` |
| `crates/qingjian-core/src/english/edit.rs` | `within_one_edit()`，~40 行 |
| `assets/lexicon/english.tsv` | 資料，94,568 詞，~2MB |

JS 版建議：

```js
// 同构：HashMap 用 Map，排序数组用 Array + binarySearch
class WordList {
  constructor(tsvText) {
    this.byCode = new Map();     // 小写编码 → { code, word, freq }
    this.sorted = [];            // 按 code 排序，供 complete() 二分
  }
  get(code) {}
  complete(prefix, limit) {}     // 二分找起点 + takeWhile + 按 freq 排序
  entries() {}                   // 全扫，供纠错用
}
```

接入點：在 `renderer/ime.js` 的 `onCompositionUpdate` 之後，加一個平行的英文候選管線，與 jszhuyin 的注音候選並列顯示。

### 5.2 中等：中英混輸（需要拼音切分能力）

路徑 ②（整段是英文詞）需要判斷「這段拼音像不像話」。青简靠 `parser::segment()` + `correction::unlikely_pinyin()`。

你的工具是注音不是拼音，這個判定邏輯不同——注音的「不像話」判定應該是「符號序列切不出合法注音符號組合」。但**候選位置的四條規則**（拼音不像話 / 不壓過學習記錄 / 短縮寫例外 / 例外只管沒選過的）是可以照搬的。

### 5.3 困難：拼音頭 + 英文尾（不建議照搬）

路徑 ③ 依賴：

- `parser::segment()` — 拼音音節切分
- `parser::is_fully_segmentable()` — 能否完整切分
- `convert_sentence_with()` — 整句轉換 + 打分
- `static_score` / `penalty` — 語言模型得分

這是整套拼音引擎的能力，不是獨立模組。注音工具要實作等價物，工作量接近重寫引擎。

**但「比分決策排除個人加成」這個設計原則值得記住**：任何「用哪種輸入方式」的策略判斷，都該由靜態模型定，不歸個人頻次管。個人頻次只負責「同樣策略下選哪個詞」。

### 5.4 中等：釋義表顯示

如果要加譯詞顯示：

1. 拿 `glossary-en.tsv`（中 → 英）或自己生成一份注音 → 英文的表
2. 格式就是 `词\t译文1\t译文2`，解析很簡單
3. 在候選渲染時查一次表，查不到留空

不需要 mmap、不需要 `.qj`、不需要雲端兜底——`Map.get()` 就夠。資料量如果不不大（幾千條），JSON 或 TSV 都行。
